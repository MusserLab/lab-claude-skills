# GitHub and Hybrid closeout

Load this only for a valid GitHub or Hybrid declaration and a material event involving already
identified Issues. The coordination model comes from
[Work coordination](../../new-project/references/work-coordination.md). Missing access is a
limitation, not authority to switch task state into Markdown.

## Establish current authority and evidence

Use the exact repository and Issue(s) already identified by the user/session. Read current body,
relevant comments, state, milestone, and update time. Inaccessible/private is not absent. Do not
automatically select or create Issues, milestones, labels, boards, or a new task scheme.

For GitHub, Issues own executable scope, dependencies, state, and completion. Meaningful comments
can preserve decisions, evidence, verification, limitations, handoff, or acceptance. No material
event means no Issue write. For Hybrid, update the programme plan only for intent, consequential
decisions, phase boundaries/relationships, and human acceptance; link the Issue without copying
its task state.

Architecture, scientific reasoning, active-file/data authority, provenance, validators,
ratification, and scientific/programme acceptance remain in their established records. Issue
closure supplies none of them automatically.

When implementing or delivering work for an already identified Issue, the responsible agent updates
the owning Issue and directly affected related Issues' current summaries at the substantive handback
when those writes are already authorized; `done` catches any unfinished reconciliation. Include direct
incoming references that still call completed work pending or blocking. Comments alone do not correct
those summaries. Preserve history and unrelated remaining scope; correcting a closed Issue's stale
current summary does not require reopening it. Do not expand this into a queue-wide or transitive
dependency audit. Without write authority, preserve the exact proposed updates in the handoff.

Close verified completed agreed scope within existing authority. Possible future information or
optional improvements are not reasons to keep an Issue open or invent a new observation gate.
Preserve specific unmet obligations and agreed human acceptance gates. Later evidence can justify
reopening the original incomplete/recurring problem or creating a linked Issue for distinct new
scope; this does not erase the earlier resolution or authorize new implementation or delivery.

## Prepare the concrete external action

Before an Issue mutation, make the result reviewable:

| Action | Required evidence |
|---|---|
| Existing body edit | Exact Issue, current baseline, and complete proposed diff preserving unrelated content. |
| Meaningful comment | Exact destination and full text, with supporting evidence and limits. |
| Existing milestone assignment | Exact repository milestone and current/proposed assignment. Do not create/redefine milestones here. |
| Closure | Exact resolved scope and verified supporting record; any scientific/behavioral acceptance assigned to the researcher must already be recorded. Routine closure may proceed without repeated approval only when the repository's current policy already authorizes it. |

Identify dependencies on local verification/Git, architecture/configuration, or other actions.
Use existing authorization for its exact unchanged scope; ask only when this external action was not
already authorized or its baseline/scope materially changed. Approval to edit/commit/publish is not
acceptance.

Git already authorized by the task and native user or project instructions follows core `done`; it does not require an Issue approval package.
Public/shared/collaborator publication and deployment retain their separate boundaries. Disclose
the actual outgoing commits when a proposed Issue claim depends on their publication.

## Execute in dependency order and read back

1. Recheck the relevant Issue field/comment/state immediately before mutation. Preserve concurrent
   changes and revise the proposal when they affect scope or authorization.
2. Complete required local verification and Git actions before publishing claims that depend on
   them. A failed/held action blocks dependent claims, though an independently authorized factual
   failure comment may still proceed.
3. Apply only the authorized field-specific body/comment/milestone change. With a CLI, use a literal
   body file for multiline text rather than shell interpolation. Read back each changed body and state.
4. Apply authorized closure last and verify the actual Issue state and closure reason.
5. Reconcile succeeded, failed, held, and unverified actions in the final handback and the project's
   existing chronological record when it uses one.

Issue-only work needs no invented code commit. A chronological record changed by the session still
needs truthful Git accounting under its project convention.

## Unavailable or uncertain outcomes

- If GitHub is inaccessible or the tool lacks access, preserve the exact pending text in an
  authorized private handoff location or chat. Do not infer absence or create a local task backlog.
- If a mutation times out or returns an uncertain response, inspect actual state before retrying to
  avoid duplicate comments or overwritten bodies.
- If only part succeeds, record each result separately and hold dependent closure/actions.
- If readback is missing or mismatched, call the write unverified and preserve the observed result.
- If a prerequisite commit/push is held or fails, dependent publication/closure remains pending.

Never claim acceptance or closure from a prepared payload, passing test, successful-looking API
response, or publication alone.
