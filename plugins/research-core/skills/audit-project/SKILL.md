# Project audit and optional consolidation

Establish what the project needs to preserve and what a fresh agent needs to find. Audit a
bounded project scope using current instructions, authoritative records and evidence.
An audit proposes changes; it does not itself authorize project adoption, scientific-method
changes, acceptance, deletion, synchronization or publication. Do not run this as mandatory
session closeout or migrate projects simply because shared instructions changed.

## Orient and establish authority

Explain the project purpose, the audit's scope and why it matters. Read root instructions,
applicable nested/override instructions and the Project Document Registry before inspecting
registered scripts or data. Verify host, physical checkout, branch and dirty state; preserve
unrelated work. Inspect current evidence rather than inferring defects from names or age.

Read the explicit coordination declaration using
[Work coordination](../new-project/references/work-coordination.md) and its read-only reader.
Keep project type independent of coordination:

- Plan/undeclared: preserve the existing planning authority and formats.
- GitHub: Issues own executable work; registered scientific/data/architecture records retain
  their roles. Missing task plans are not defects.
- Hybrid: plans own programme intent, consequential decisions, phase boundaries and human
  acceptance; linked Issues own executable work. Do not mirror Issue status into plans.
- Invalid, conflicting or duplicate declarations: report the ambiguity and hold dependent
  edits or inferred GitHub actions. Unavailable Issues are unknown, not missing work.

General projects do not acquire scientific directory or script-format conventions. Preserve
collaborator/private overlays and host-specific paths. Record evidence scope and check time.

## Inspect meaning and navigation

Use targeted searches and delegate independent project areas when useful. Give workers the
shared authority context; one lead reconciles cross-document meaning. No fixed worker count,
tool, solo-only phase or mandatory fan-out. Do not audit all historical science merely to
shorten instructions, and do not rerun expensive work without its execution/resource scope.

For the relevant records, examine:

- **Discovery:** can a fresh agent follow the root registry to current inputs, producers,
  results, decisions and unfinished review? Test representative routes through actual links.
  The root registry describes roles; manifests, schemas, producer validation/provenance and
  human decisions retain authority for their declared subjects or fields. Several sources
  may be necessary. Do not demand a new prose document for every dataset or script.
- **Agreement:** identify contradictory current claims, broken links, missing significant
  records and obsolete rules. Label historical evidence and dated resumption cues. Old logs
  do not override current work authority, and unavailable evidence does not prove completion.
- **Scientific meaning:** preserve accepted scope, reasoning, warnings, source/version
  distinctions, input and producer lineage, evidence, limitations, downstream restrictions,
  and unfinished review. Keep [semantic closure](../planning/SKILL.md#assemble-register-and-preserve-meaning)
  and existing validators or ratification records. Execution, Issue closure, audit findings
  and review-depth choices are not scientific acceptance. Do not retrofit every old plan.
- **Useful root content:** retain concise descriptive registries, stable environment/run
  guidance, critical warnings and unique rationale. A short inventory may help a stable
  project. A brief always-present boundary plus practical skill detail is legitimate.
  Code patterns alone do not prove that a warning is dispensable. Length is not a defect.
- **Active files and outputs:** consult registered authority and actual consumers. Missing
  lifecycle labels, numbered `.py`/`.R`/`.Rmd` files, old timestamps or unmatched directory
  names alone are not defects. Preserve supersession warnings and retained outputs. A
  terminal figure need not be read by another script; ignored/generated does not mean disposable.
- **Exploratory work:** inspect each project's actual exploratory/scratch conventions and
  retained dependencies. Record what the separation helps, what reads it and what a move
  would break. Keep, simplify or retire only with evidence and scoped adoption. Do not ban
  a dependency because its directory is named `exploratory` or move files merely to tidy it.
- **Environment and provenance:** check relevant input identity, actual producing-state
  evidence and environment/run guidance. Development from uncommitted code is not automatically
  invalid, but retained scientific use requires the relevant producer, wrapper, helpers and
  configuration to match a focused commit. Unrelated dirty work does not invalidate that match,
  and unchanged relevant source needs no new commit. Preserve existing project-specific custody
  records; do not demand a generic source-copy bundle in `outs/`. Shared
  worktrees need explicit inputs, compatible environments and separate outputs; do not
  copy datasets or create environments per worker. A worktree does not isolate an installed
  dashboard, live ledger, scheduler or other external state. Inspect those dependencies before
  a project pilot. Existing explicit project contracts remain until separately scoped adoption.

Check dependency specifications only where the scope or evidence indicates a change. Do not
rebuild STATUS_SUMMARY, prune user memory, scan unrelated global skills or impose log-entry
limits as part of every audit. Existing summary conventions can be reviewed when explicitly
in scope; keep the overview redesign separate.

## Propose the smallest useful consolidation

Produce a concise stay/move/remove mapping with the source, proposed destination or retained
pointer, reason, affected consumers and verification. This is a one-time review aid, not a
paragraph ledger. Establish an adequate destination before moving unique content. Distinguish
redundancy from repeated useful navigation and explain any apparent conflict before pruning.
Preserve any project-defined author/producer classes: generated records must be regenerated by
their producer and human-only decisions/ratification cannot be rewritten as document cleanup.
Do not invent a universal authorship taxonomy for projects that do not define one.

Show concrete consequential conflicts with a recommendation; reuse settled user decisions.
Do not reopen a broad policy interview. Separate document reorganization from scientific,
method, acceptance, coordination-model or data-custody changes. Preserve meaningful history
and accepted decisions rather than rewriting them to look like the current convention.

Before using a newly revised shared consolidation procedure, obtain bounded compatibility
reviews in representative projects. Reading a project for that review authorizes no migration.

## Apply only the project's scoped adoption

When the particular project and proposed change are explicitly authorized, make the bounded
reversible edit, preserving unrelated state and a rollback source. Recheck changed baselines
and dependent consumers. Routine implementation of that approved scope needs no repeated
permission, but consequential new conflicts return to the user before dependent work.

Verify that representative root-registry routes still reach the correct active files and
records, that unique rationale/warnings and unfinished acceptance remain discoverable, and
that relevant callers, host paths and selected workflow still work. Use focused link/parse
or smoke checks suited to the diff; do not rerun science solely for document reorganization.
Update affected registry entries when their role changes. Retain exact deployment/adoption
and check scope; source review is not natural-use evidence or scientific acceptance.

## Report and preserve evidence

Return consequential findings, recommendations, actual changes/checks and limits, with source
links. Reuse an appropriate existing issue, plan, audit report or log for a concise integrated
record; create another report only when useful. A lack of findings applies only to inspected
scope. Do not claim project-wide health from a partial search.

For an explicitly report-only or scheduled invocation, perform detection only: ask no questions
and make no project changes except the requested report. Preserve the scheduled caller's
established audit-report output contract when one exists; inspect its prompt and scope. Report
unknown or inaccessible sources. Do not create Issues, alter task state, rebuild overviews,
adopt the candidate or run an automatic repair because an audit was scheduled.
